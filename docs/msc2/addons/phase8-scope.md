## Add-on identity, update precedence, and source persistence

`AddonUpdateResolver.swift` (313 lines, pure — "no AppViewModel dependency" per its own header) is the whole story for **installed add-ons already on disk**, independent of `PluginSourceConfig`/GitHub/Hangar/direct sources:

1. **Enumerate** every `.jar`/`.jar.disabled` in the add-on folder (`plugins/` or `mods/` per `JavaServerFlavor.addOnKind`).
2. **Exclude Geyser/Floodgate on plugin servers only** (line 129-138) — installed from GeyserMC's CDN via a dedicated updater (Phase 9's `PluginDownloader.swift`), not Modrinth-hash-resolved. Mod servers keep them in the resolve pass because Fabric/NeoForge builds of Geyser have no dedicated updater. This exclusion is add-on-kind-conditional, not a blanket skip — P8.16's inventory must reproduce the same conditional, not a flat exclude list.
3. **Hash every file** (streaming SHA-512, `ModrinthAPI.sha512Hex`) — the exact-identity mechanism; SHA-1 exists as a declared fallback algorithm (`sha1Hex`) but the resolver never actually calls it.
4. **Identify + plan in two batched calls**: `versionsFromHashes` (exact installed-version identity) and `latestVersionsForHashes` (server-computed "latest compatible build," filtered by the server's `modrinthLoaderFacets` and `minecraftVersion`) — both run concurrently via `async let` (line 154-157), so a folder of 30 add-ons costs two Modrinth requests total, not sixty.
5. **Resolve identity, in this exact fallback order** (line 174-177): hash match → persisted `addonLinks` entry matching `installedHash` → persisted `addonLinks` entry matching `installedFileName`. Only when all three miss does an item fall to `.unlinked`.
6. **Bucket** each identified item into `updateAvailable` / `noCompatibleVersion` / `upToDate`, by comparing the latest-compatible version ID against the installed version ID (falling back to the *persisted* `installedVersionId` when no fresh hash-identify hit, so a manually-linked add-on whose exact version Modrinth doesn't independently confirm still gets a real up-to-date/available comparison, not a false "no compatible version").
7. **Provenance** (`AddonLinkProvenance`: `installed` / `hashDetected` / `userLinked` / `nameGuess`) drives trust: only `hashDetected` links get freshly re-recorded every resolve pass (self-healing); a `userLinked` entry's `provenance`/`title`/`slug`/`iconURL` survive a later hash-detect merge untouched — only its `installedVersionId`/`installedFileName`/`installedHash`/`clientSide`/`serverSide` get refreshed (`AppViewModel+AddonUpdates.swift::mergeDiscoveredLinks`, line 53-72). `nameGuess` is the one provenance value the resolver itself never produces (it's assigned by the manual-link UI); `isTrusted` is `false` only for it.
8. **Stable sort**: updates first, then no-compat, up-to-date, unlinked; A→Z within each bucket by display name — a UI convention worth preserving exactly since P8.24's route response ordering should match it for a deterministic contract, not just a deterministic screen.

**Stale-plan caching (P8.5's own subject).** `resolveAddonUpdates(for:force:)` is resolve-once-with-cache: a per-server `addonPlanServerId` marker gates recompute, so calling it on every screen appearance is free; every mutation path (`invalidateAddonPlan()`) explicitly busts it. **D-021 applies directly here**: MSC 1's cache is one unbounded in-memory array for whichever server is currently selected in a single-user GUI. A headless agent serving `GET /v1/addons` for any server on demand has no "currently selected server" — P8.16's port needs an explicit per-server bound (LRU or TTL) on how many resolved plans it holds at once, not a straight port of "one array, most recently computed."

**Source persistence and rekeying (P8.5's `plugin_source_mapping` fixtures).** `setPluginSource`/`removePluginSource` (`AppViewModel+PluginManagement.swift:216-253`) key `pluginSources` by `jarStem`, and defensively strip any *prefix-matching* old key before writing a new one (line 223-226) — guarding against a stale entry surviving a version bump that changed the filename stem. `downloadLatestForPlugin` (line 302-381) rekeys for real after a successful download: if the new file's stem differs from the old, it writes a fresh `pluginSources` entry under the new stem and removes the old one (line 357-368) — this is the mechanism P8.5's "source-key rekeying after versioned filename changes" fixture must characterize byte-for-byte, including the prefix-based old-JAR-removal sweep (line 344-352) that runs before the rekey.

## Dependency resolution — depth guard, not cycle detection

`installRequiredDependencies(of:into:depth:)` (`AppViewModel+ModManagement.swift:271-328`) only installs `dependencyType == "required"` Modrinth dependencies (optional dependencies are never auto-installed — matches `rolling-plan.md`'s own "Optional dependencies remain explanatory, not silently installed"). Two things P8.12/P8.15 must not silently improve past without documenting the change:

- **The "cycle guard" is a flat recursion-depth cap of 3** (`guard depth < 3`, line 275), not a visited-project-ID set. A genuine A→B→A cycle is only prevented because the recursion happens to bottom out at depth 3, not because MSC 1 detects the cycle as a cycle — a length-4 cycle would still terminate (depth cap), but a diamond dependency (A needs B and C, both need D) would attempt to install D twice were it not for the separate "already installed" checks (mod-ID match against `discoveredMods`, then a filename-contains-slug scan of the folder, line 288-294) that run *before* each recursive call, independent of the depth cap.
- **No true cycle *detection*** exists to distinguish "this is a cycle" from "this dependency tree is just deep." P8.12's domain port should build a real visited-set cycle detector (the "reject or terminate cycles" language `rolling-plan.md`'s P8.15 already commits to) as a **deliberate strengthening**, the same class of change Phase 7 made explicit for its own rollback unification — not a byte-for-byte port of the depth-3 guard, which P8.6's fixtures should characterize as MSC 1's actual (weaker) behavior for oracle-faithfulness, while P8.12's domain logic implements the stronger, decided contract.

## Client-only classification — two different precedence chains, not one

`ModpackClientOnlyClassifier.swift` (147 lines) defines four tiers, but **the actual call order differs by which path a jar arrived through** — this is the one correction most worth flagging before P8.6 writes fixtures assuming a single universal pipeline:

- **Manifest-listed `.mrpack` files** (the common case): **Tier 1 only, pre-download.** `isManifestServerUnsupported(_:)` filters `env.server == "unsupported"` entries out of the download list entirely (`importModpack`, line 481-484) — those files are never written to disk. Once downloaded, `classifyAndDisableManifestJar` runs **Tier 2 (Modrinth `server_side`) then Tier 3 (embedded jar `environment`)** — Tier 0's hardcoded blocklist is **never consulted for manifest-listed files**, because BMC4-style packs mis-marking real mods as `server=required` is exactly the failure Tiers 2/3 exist to catch, and the known-list is redundant once a manifest entry already survived Tier 1.
- **Override-tree jars and every CurseForge-imported jar** (no per-file manifest env available at all): **Tier 0 first, Modrinth/jar fallback second** — `disableClientOnlyOverrideJars` computes `knownClientOnlyReason(forJarStem:) ?? clientOnlyReason(modrinthServerSide:...)` (line 794-796) — because Forge-only shader/renderer mods (`oculus`, `mekalus`, `rubidium`, `embeddium`, `iris`, `optifine`, `optifabric` — prefix-matched against the lowercased jar stem with `-`/`_`/`+` separator rules, `ModpackClientOnlyClassifier.swift:27-51`) carry no `fabric.mod.json` (Tier 3 blind) and frequently aren't listed on Modrinth with `server_side=unsupported` either (Tier 2 blind).
- **Modrinth wins over the jar's own embedded environment whenever Modrinth has an opinion at all** (`clientOnlyReason`, line 94-111): `server_side` present and *not* `"unsupported"` returns `nil` (keep enabled) even if the jar's `fabric.mod.json` says `environment=client` — many single-jar mods ship a client-facing manifest but run fine server-side, and Modrinth's own curated field is trusted over the embedded one. Tier 3 only fires when Modrinth has no data at all for that hash (unlisted project, or the batch lookup failed offline).

`rolling-plan.md`'s own working exit criteria phrase this as one "manifest, Modrinth, embedded JAR, known-list" precedence order — accurate for the override/CurseForge path, but the manifest path never touches the known-list at all. P8.6's fixtures need both paths as genuinely separate cases, not one shared "apply all four tiers in order" fixture set.

**Two ledgered gaps, already flagged at ledger time** (`msc2-symbol-ledger.csv`, `ModpackClientOnlyClassifier.swift` rows): `knownClientOnlyReason` (line 40, no P0.17 fixture — this Tier 0 blocklist was undiscovered until the ledger pass) and `disabledURL(forActiveJar:)` (line 122, trivially "append `.disabled`," but also uncovered). Both need fixtures alongside the rest of P8.6 rather than being assumed already covered.

**Never-clobber, in both directions.** `disableJar(at:fm:)` (line 131-146) never overwrites an existing `.jar.disabled` — if one is already present, the freshly-downloaded active duplicate is deleted instead. `importModpack`/CurseForge import both check for an existing `.jar.disabled` sibling *before* downloading at all (line 500-502, 646-648) and count it as "already present" — a prior import's disable decision survives a re-import untouched, even if the file would newly re-download.

## Pack-managed guard — MSC 1 has none; Phase 8 must invent real enforcement

**This is the single most consequential finding in this note.** `packManaged`/`packName`/`packVersion` are real, persisted `ConfigServer` fields (`AppConfig.swift:259,318,394,452`), set at import time by both the `.mrpack` and CurseForge importers (`AppViewModel+ModManagement.swift:474-479`, `615-620`). But grepping every production call site of `packManaged` across the whole codebase shows it is read in exactly two places, both **SwiftUI confirmation-dialog copy**:

- `DetailsComponentsTabView.swift:1148-1157` — an update-confirmation alert's message text adds a sentence ("This server was installed from *Pack Name v1.0*. Updating individual mods may break the pack's tested version set.") when `packManaged` is true. The alert's **destructive action button still calls `removeMod`/`removePlugin` unconditionally** either way — the flag changes wording, not whether the mutation proceeds.
- `AddonUpdateSheet.swift:272-277` — before calling `updateAddons`, shows a confirmation sheet (`showPackManagedAlert`) when `packManaged` is true; nothing in the surrounding code prevents the user from confirming through it.

**No production code anywhere — not `AppViewModel+ModManagement.swift`'s mutation functions, not `RemoteAPIServer+ComponentRoutes.swift`'s route handlers, not `AppViewModel+APIWiringAddons.swift`'s wiring — checks `packManaged` before allowing `installModrinthAddon`, `removeMod`/`removePlugin`, `toggleMod`/`togglePlugin`, or the remote API's install/remove/update handlers to proceed.** The remote API only ever *reports* `packManaged` as a read-only field on `GET /v1/addons`'s response (`AppViewModel+APIWiringAddons.swift:95`); it never gates a write.

`rolling-plan.md`'s own working exit criteria already commit to real enforcement — "Pack-managed servers refuse individual mutation while still allowing an explicit whole-pack replacement path" — so this isn't a question for Cameron; it's **new agent-owned policy Phase 8 is building, not a port of an MSC 1 guard, because no such guard exists to port.** P8.12's domain layer should treat the pack-managed mutation matrix as original design work characterized against the *decided* contract (P8.6's `fixtures/pack-managed-guard/`), not against MSC 1's behavior, which is "always allow, warn in English." The explicit whole-pack-replacement escape hatch (re-running the same pack importer against an already-pack-managed server) has no MSC 1 precedent either — `importModpack`/CurseForge import both run unconditionally regardless of the server's current `packManaged` state, so "replace" and "first import" are, today, literally the same code path with no re-import guard of any kind.

## Modpack create/import boundary

**MSC 1 has no pack-driven server-creation primitive.** `importModpack(from:for:)` and `importExtractedCurseForgeModpack` both take an **already-existing** `ConfigServer` (`for cfg: ConfigServer`) and mutate its `mods/`/`plugins/` folder in place. The wizard's "create a server from a modpack" experience is built by composing two independent, already-existing mechanisms, not by a dedicated pack-create function:

1. `createNewServer` provisions a completely ordinary server first (jar/installer, `eula.txt`, `server.properties`, add-on folder, world slot — every step `phase7-scope.md`'s "Cross-family creation mechanics" already documents) — the pack has already been sniffed for its pinned Minecraft/loader version via `readMrpackMetadata`/`readCurseForgeMetadata` so the wizard pre-selects the right `ServerVersionEntry`, but nothing about the pack's *mod list* has been touched yet.
2. Only after the server directory, jar, and initial world slot all succeed does `applyStagedAddOn` iterate the wizard's staged add-ons (`AppViewModel+ServerCreation.swift:368-378`); its `.mrpackFile`/`.curseForgeFile` cases (line 698-704) call the exact same `importModpack(from:for:)` used for importing a pack into a pre-existing server — **there is no separate "create from pack" code path in MSC 1 at all.**

**The consequence for rollback.** `createNewServer`'s outer `catch` (`AppViewModel+ServerCreation.swift:690-696`, per `phase7-scope.md`'s own step 14) only fires on a **thrown Swift error**. `applyStagedAddOn` and everything it calls — `importModpack`, `importExtractedCurseForgeModpack`, every branch of the staged-add-on switch — **catch their own errors internally and log them (`noteCreation`/`logAppMessage`), never `throw`.** This means: today, a modpack whose downloads partially fail during a wizard-driven create still results in a **published, registered server** with a half-installed mod folder — the outer rollback path is structurally unreachable from a pack-import failure, not merely untested. `rolling-plan.md`'s own P8.21 working exit criterion — "Do not publish the server registry entry until loader provisioning, pack application, initial world setup, and pack provenance all succeed; rollback the directory and staged artifacts on every failure or restart" — is therefore **new rollback discipline Phase 8 must build, extending Phase 7's create-rollback precedent to a failure class MSC 1's own creation flow structurally cannot roll back from today.** P8.7's fixtures should characterize MSC 1's actual (non-rolling-back) behavior for oracle-faithfulness; P8.21's application code implements the stronger, decided contract — the same split already applied to the dependency cycle guard above.

**No rollback for import-into-an-existing-server either.** `importModpack`/CurseForge import against an *already-running* server (not creation) leave whatever was downloaded before a failure exactly where it landed — `failed.append(...)` accumulates a list that's only ever logged, never used to undo. `rolling-plan.md`'s working exit criteria only promise transactional behavior for the **create** path ("archive traversal, corrupt downloads, interruption, dependency cycles, and failed overrides leave no half-created server" — "server," singular, meaning the new one); a pack *update* against a live server replacing files in place is a separate, lower-stakes case this note does not read as needing the same all-or-nothing guarantee, but P8.19/P8.20 should decide and document this explicitly rather than let it default silently.

**Zip extraction is macOS-only in the oracle, on three separate call sites.** `readMrpackManifest`, `readCurseForgeMetadata`, `importModpack`'s own extraction, and `applyStagedAddOn`'s `.zipFolder` case all shell out to `/usr/bin/ditto -x -k` (chosen over `/usr/bin/unzip` specifically to dodge a mode-000-permission-bit extraction quirk — `AppViewModel+ModManagement.swift:412-414`); `ModJarMetadataParser.swift` separately shells out to `/usr/bin/unzip -p` to read one entry at a time from inside a jar; `AppViewModel+ClientExport.swift`'s `writeZip` shells to `/usr/bin/zip -j`. **None of these five call sites survive the port as external-process calls** — `msc2-decisions.md`'s D-006/D-011 headless-tri-platform requirement and this phase's own P8.14 text ("use Rust ZIP support, never `ditto` or `/usr/bin/zip`") both already settle this; recorded here as confirmation the oracle read agrees there is no macOS-only behavior worth preserving in any of the five, not as a new finding.

## Rollback and cancellation — summary table

| Workflow | MSC 1 rollback today | Phase 8's decided contract |
|---|---|---|
| Single add-on install/update (`installModrinthAddon`, `applyAddonUpdate`) | Download to final name directly (no temp-then-rename); old file removed only *after* the new one is already in place, no hash check against Modrinth's published hash before commit | P8.14: stage into an operation-owned temp area, verify publisher hash when present, atomic replace |
| Dependency chain (`installRequiredDependencies`) | None — a failure mid-chain logs and continues to the next dependency; already-downloaded siblings stay | P8.15: roll back this operation's newly-installed files on terminal failure |
| `.mrpack`/CurseForge import into an **existing** server | None — failed files accumulate in a log-only list; overrides that fail to copy are also log-only (`mergeDirectory`'s `failures` count, never enforced) | P8.19/P8.20: explicit decision needed on whether an in-place update gets the same all-or-nothing guarantee as create (open — see above) |
| Pack-driven **server creation** (wizard) | Structurally unreachable — `applyStagedAddOn` never throws, so the outer create `catch` can't see a pack failure; a partially-packed server still gets registered | P8.21: do not publish the registry entry until pack application fully succeeds; roll back the directory and staged artifacts on any failure or restart |
| CurseForge author-blocked file | No cancellation concept — the sheet just sits open until every file is found or the user closes it | P8.20 (per D-027 above): pending file bound to its operation; wrong/missing file leaves the operation honestly pending/failed, never publishes a half-server |

## Client export — Paper-like link list vs. modded ZIP

`buildClientExportItems(for:)` (`AppViewModel+ClientExport.swift:69-146`) classifies every enabled/disabled jar in the add-on folder by `ClientSideStatus` (`required`/`optional`/`serverOnly`/`unknown`), sourced from a persisted `AddonLink.clientSide` first, then `fabric.mod.json`'s `environment` for unlinked Fabric mods, else `unknown`. Two behaviors specific to this domain, not shared with the update resolver:

- **Geyser/Floodgate are excluded from export entirely** (`stemLower.contains("geyser") || stemLower.contains("floodgate")`, line 93-94) — bedrock-compatibility plugins, not something a Java client installs.
- **Plugin (Paper-like) servers additionally drop anything `serverOnly` or `unknown`** (line 118) — "almost always server-only" is the stated rationale; **modded servers keep `unknown` items** (only the plugin branch filters them), so a Fabric/Forge server's export list is deliberately more inclusive than a Paper server's.

Delivery differs by add-on kind, not configurable independently of it: Paper-like servers get `copyClientLinksToClipboard` (a plain-text `• Name: https://modrinth.com/project/slug` list, clipboard only — no file produced, no route needed for the link case beyond returning the same classified list); modded servers get `exportClientModsAsZip`, a flat (`zip -j`, junked paths) archive of the selected jars' raw bytes, named `{serverName}-client-{mcVersion}.zip`. `rolling-plan.md`'s P8.22 correctly scopes the **ZIP** production to Rust archive code with a documented size ceiling and no base64; the **link-list** case has no analogous size concern (it's already just JSON) and needs no equivalent new limit — recorded here so P8.9 doesn't invent one where MSC 1's own shape doesn't need it.

## GET /v1/components and components-versions — mostly not this phase, despite the name
