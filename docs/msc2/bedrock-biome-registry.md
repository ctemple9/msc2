# Bedrock numeric biome registry proof

## Observed on the private BDS save

P18.2i reads 3D biome IDs at block height. The ice mountain tile's save
reports `lastOpenedWithVersion = [1, 26, 31, 1, 0]` and `StorageVersion = 10`.
The chunk reader returns numeric IDs from the decoded biome palettes, but
the chunk record does not supply the matching biome names. ID `190` appears
in 324,336 non-air block positions below this tile's surface, while it does
not appear in the surface column count. This confirms that 3D sampling is
necessary and that surface counts cannot validate the entire palette.

## Candidate registry and exact-version gap

PocketMine's [BedrockData](https://github.com/pmmp/BedrockData) contains a
CC0 [`biome_id_map.json`](https://github.com/pmmp/BedrockData/blob/master/biome_id_map.json)
generated by a BDS mod. It maps the sample IDs `4`, `183`, `185`, `188`,
`189`, and `190` to forest, frozen peaks, grove, dripstone caves, stony peaks,
and deep dark. Its adjacent
[`protocol_info.json`](https://github.com/pmmp/BedrockData/blob/master/protocol_info.json)
reports version `1.26.30`, while this save reports `1.26.31`. Matching
sample values give useful corroboration but cannot establish that *all* IDs
are stable between these versions. The repository was archived in August
2026, so it cannot be assumed to cover future Bedrock versions.

The copied MSC1 server includes a BDS ELF executable, but the executable's
numeric biome table has not been extracted. The supplied Bedrock behavior
packs provide names and climate values; they do not establish numeric IDs.
Mojang's [biome documentation](https://github.com/Mojang/bedrock-samples/blob/main/documentation/Biomes.html)
describes namespaced identifiers and behavior-pack biome definitions, but
does not provide the save's numeric mapping.

## Required resolver boundary

1. Capture a numeric ID-to-name map from the *exact* BDS version used to
   write or upgrade a world, preferably by an exporter running against that
   server's biome registry. Record its version, source, hash, and license.
2. Match that version to the save's recorded version before assigning names.
   A nearby version is diagnostic evidence, not an automatic match. A world
   whose chunks span an upgrade also needs explicit compatibility evidence.
3. Resolve the names against that server's active behavior packs for climate
   and the viewer's resource pack for colors. Unknown or custom IDs stay
   `unmapped` with a neutral tint and an explicit coverage count.
4. Surface coverage by ID and by rendered block height in the export
   summary. Do not claim a Bedrock biome legend is accurate while any
   visible ID depends on a provisional name.

The earlier ice mountain tint was a **bounded visual proof** using provisional
IDs, not a general Bedrock registry. The exact-version registry boundary and
mismatched-version rejection were subsequently added to the converter. Named
legend entries still require a map appropriate to the save version. This
keeps the Bedrock UX honest while terrain rendering can continue independently.

## Bedrock 1.26.60 mapping in the Anvil converter

The converted-region path bundles a version-bound numeric biome map for saves
whose `lastOpenedWithVersion` is exactly `[1, 26, 60, 0, 0]`. The pinned source
is the MIT-licensed [Chunker Bedrock biome ID fixture](https://github.com/HiveGamesOSS/Chunker/blob/50aaf6d82e8b68929279161b790d95fdddfe0a40/cli/src/test/resources/bedrock/resolver/biome_ids.json),
with SHA-256 `254bfef4d4ac95dd71c439e6340aa6b6fe881c462d59d1e492af652a3a9d4522`.
Chunker's [resolver](https://github.com/HiveGamesOSS/Chunker/blob/50aaf6d82e8b68929279161b790d95fdddfe0a40/cli/src/main/java/com/hivemc/chunker/conversion/encoding/bedrock/base/resolver/biome/BedrockBiomeIDResolver.java)
gates newer IDs by Bedrock version. The bundled file has 89 unique IDs and
covers all 60 IDs in Bedtonic's existing conversion report. This evidence
supports using it for Bedtonic; it is not an extraction of the exact BDS
binary and does not prove that chunks carried through a world upgrade contain
only IDs from that version. Any ID absent from the map stays explicitly
unmapped, with a neutral tint, and appears in the conversion report.

The converter uses the bundled map for any save reporting that exact version,
so it is not tied to Bedtonic or Cameron's computer. Other versions need a
separately sourced map. Without one, numeric IDs remain visibly unmapped;
they are never silently renamed `plains`. A caller-supplied registry still
requires an exact metadata-version match. The conversion and detailed-tile
cache identities changed because older output flattened unknown biomes to
`plains`; correcting them requires one new conversion and tile bake. Old
private caches are left intact for later cleanup.

P18.92's physical check exposed a separate converter bug: the numeric ID map
was present, but block subchunk key `4` was used to look up a Data3D biome
storage keyed by block Y `64`. Every sample became the missing sentinel
`4294967295`. P18.93 aligns those coordinate systems, preserves the legacy
2D fallback, and advances the conversion and tile cache identities again.
The corrected output requires a fresh conversion; the P18.92 cache cannot be
reused because its Anvil biome palettes contain the sentinel.

## P18.2k registry input boundary

The exporter accepts an optional fifth positional argument after the chunk
origin: a JSON registry with `version` (five integers), `source`,
`source_sha256`, and `ids` (name-to-unique-integer map). It compares all five
version components to the save's `lastOpenedWithVersion`, validates unique
numeric IDs, and checks the five names currently used by the bounded tint
proof. A mismatch stops export before writing a tile. Without a registry,
the export stays explicitly `provisional` in `summary.txt`.

The archived BedrockData `1.26.30` map was downloaded outside Git to
`/private/tmp/msc-biome-registry-1.26.30.json` for Cameron's mismatch check.
Its raw map SHA-256 is
`4f27df3f1e58476fc65e337f7cf3e275f65a98b6c40ea46c31b24016b85e0052`.
The supplied executable is named `bedrock_server-1.26.31.1`. Docker Desktop
was started and a disposable Linux container confirmed that this copied
binary exposes no biome symbols in its dynamic symbol table. The
[BDS mapping mod](https://github.com/pmmp/bds-mod-mapping) needs a moddable
server binary and toolchain. Its developer kit was cloned outside Git, but
the original archive with any additional symbol files could not be obtained:
the official archive download stalled before transferring data. An exact
`1.26.31.1` registry was therefore **not** obtained. The private `1.26.30`
wrapper pads BedrockData's four-part version with a fifth zero for the
rejection check; that pad is not source metadata. The guard validates
metadata and source fields; it does not authenticate that a claimed map was
actually generated by BDS. A world upgraded across versions may also hold
older chunk IDs. Those remain open proof requirements before general support.
